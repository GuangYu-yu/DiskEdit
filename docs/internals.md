# Behaviour boundaries and limits

README keeps only "what it is and how to use it". This file records the behavioural constraints: capability gate, occupancy and concurrency decisions, target identity, recovery records, resume semantics, external tools and verification scope, plus the option table reconciled against the flag registry. Update it when these behaviours change.

## Platform capability gate

Only Linux promises safe writes. On every other platform dispatch refuses on the capability gap — no command is available, `info`/`plan`/`inspect`/`records`/`check`/`abandon` and all write commands included — with exit code 6 and the message `no command is available on this platform — diskedit supports Linux only. Nothing was written (no target bytes, lock, recovery record, or log).` The gate runs before geometry computation, lock acquisition and any companion-file creation, and before the confirmation gate.

## Occupancy boundary

Writes to a block device rely on opening the whole disk with `O_EXCL`: when any partition is mounted or used as swap, the kernel refuses the open with EBUSY; a second occupancy gate re-checks before writing (probing each partition on block devices — defence in depth). Image files have no such kernel semantics, so the gate enumerates loop devices in reverse: the `(st_dev, st_ino)` of the already-opened image handle is compared with `(lo_device, lo_inode)` returned by `LOOP_GET_STATUS64`; on a match it checks whether that loop and its partitions are mounted (walking every readable mount namespace), are active swap, or are held by a block-device stack. The decision does not depend on the `loop/backing_file` path, so hard-link aliases, deleted backing paths and mounts in other mount namespaces are all caught. The loop exclusivity this process registers is a process-level name table; every entry is re-checked against the current live mapping when consumed (the name only locates the registration). The occupancy decision matches every loop whose backing has the file's `(st_dev, st_ino)`, so it answers "this file is mapped or held", not which of several stacked mappings on the same filesystem is the one. **Commands that write the table directly** (`new`/`add`/`delete`/`set name|type|flag`/`undo`) require the target to be completely idle: any partition in use would fork the new table from the kernel's view, so the command does not care which partition it edits. `copy` is the exception — it only adds an entry in a free area after an overlap check, changes no existing extent and moves no partition's extent. Move-class commands (`resize-part`/`move`/`resize`) and `mkfs` distinguish by the shape of the write: a write that keeps the start and only extends the end is allowed on a target held only by dm (the grow semantics of LVM PVs and dm-crypt); moving, shrinking and whole-range rewrites are refused. If any enumerated loop node cannot be opened, an ioctl returns an error other than ENXIO, sysfs cannot be read, or `/proc/<pid>/mountinfo` cannot be read for permission reasons (e.g. `hidepid`), the tool refuses to write (exit code 4) as "cannot confirm" — even if that loop has nothing to do with the target; this is a safety-first environment limit, not evidence that the target is in use.

## LVM finish boundary

`pvresize`/`lvextend` for a PV inside an image run through a temporary loop mapping. If that PV is already mapped by another loop and the VG has an active LV, LVM prefers the device view "in use by an LV" over the temporary mapping, so `pvresize` against the temporary mapping has no effect (exit status still 0). The tool reports exit code 5 (stale postcondition view) from its postcondition check and prints the remedy; it does not claim success. The partition-table extension has been committed; the PV, LV and filesystem are unchanged. To finish the LVM chain in that configuration, deactivate the VG, release the user-side loop and re-run. The tool will not raise the `sizelimit` of a loop owned by another stack: when an external loop has the same offset as the request but a different `sizelimit` (higher or lower), it refuses and points at detaching and re-attaching from the layer that owns the mapping (`losetup -d <dev>`, letting the stack map again); the same applies to `--grow-lv` — without that re-attach the owner will not finish the LVM chain for you.

After a successful `--grow-lv` on a PV inside an image, `lvextend -r` leaves a previously inactive LV active, so the temporary loop cannot be detached immediately: `losetup -d` returns success, the kernel marks the loop autoclear, and the mapping is released when the VG is deactivated (`vgchange -an`). This is the lifetime of a temporary mapping, not a leak; after the VG is deactivated, `losetup -a` no longer lists the image.

## Concurrency boundary

The exclusive lock on a target is *advisory*: it constrains only processes that follow the DISKEDIT protocol, and only across their invocations. **It is not a mandatory lock against every writer on the system** and does not stop other programs, kernel-side writes, or paths that bypass this tool from writing the same target; it must not be read as a system-wide exclusivity guarantee (mechanism in the `src/targetlock.rs` module comment). The whole-disk `O_EXCL` and the mount occupancy gate only stop writers within kernel semantics. The loop reverse lookup for images is a point-in-time decision taken before writing: between the check and the actual write, an external process can still create a loop, start swap or mount the image, and this tool's lock does not constrain those processes. A table write reads the table once at parse time and writes that snapshot back at commit; before committing it re-reads the entry array and compares it entry by entry with the snapshot (slots this layer edited may already equal the target value), and refuses to write the table if any entry differs, so changes made by an outside process in the window are not silently overwritten (the repair step uses the same rule, covering add/rename/set/delete and the whole relocation and resize path). To share a target with other writers, serialise externally. The inode-level second credential is taken only on Unix; non-Unix platforms promise the lock file alone. Hard-link, symbolic-link and junction aliases each take their own lock and have their own scene; concurrent use through aliases is outside the supported boundary (`std::fs::File::try_lock` is a mandatory whole-file lock on Windows and cannot stand in for this credential).

## Device identity boundary

Recovery records for block devices live at `<state_root>/recovery/<identity-hash>/record` — the directory name is the first 16 bytes of sha256 over the identity fields (device class, stable identity string, carrier `file_id`) concatenated in order, in lower-case hex; a partition target's stable identity string is the carrier's stable string plus the partition number, so a partition node and the whole-disk node each have their own record directory. The lock is not derived per target: it lives at `<state_root>/<disk key>.lock` for the whole disk, and the two share one lock. The state root defaults to `/var/lib/diskedit`; on Linux, when euid is not 0, `DISKEDIT_STATE_DIR` is ignored; other platforms have no block-device targets and use the image-side state directory. Stable identity takes the first non-empty original text of `wwid` → `device/wwid` → `device/serial` (the last only when two reads agree); dm, md, targets with only major:minor, unreadable targets, or targets whose two reads disagree are `Unusable` — no record directory, and write commands refuse with 6. When the sysfs topology (node, `partition` attribute, parent device) cannot be read the tool likewise refuses, and does not fall back to `{devname}-{capacity}` from the caller's path. Capacity does not participate in partition identity (see `src/dev/identity.rs`, `src/dev/topology.rs`, `src/dev/host_repo.rs`). Image identity is derived from the path: it identifies "this path", not "this file". On Linux, realpath merges only symbolic links and path spellings, **not hard links**: two hard-link names of one inode derive two record directories (`<name>.diskedit/`), and a job interrupted through name A is invisible through B and cannot be resumed or undone from B — such a job must be finished under the same name. There are two lock layers: the **lock file** (block devices: `<state_root>/<disk key>.lock` for the whole disk, shared with its partitions; images: `<image>.diskedit/record.lock`; loops: a sibling lock file next to the backing file; the disk key is the device-id when present, otherwise the sysfs parent node name plus the capacity in sectors) and the **inode-level second credential** (Unix only: a lock on a freshly opened handle of `data_path` — the data file for images, the device node for block devices). The latter collapses alias paths of the same inode onto one lock; the whole disk and its partitions are collapsed by the shared lock file. Non-Unix platforms promise the lock file alone; hard-link, symbolic-link and junction aliases each take their own lock and have their own scene, and concurrent use through aliases is outside the supported boundary (`std::fs::File::try_lock` is a mandatory whole-file lock on Windows and cannot stand in).

## Identity check of a recovery scene

A recovery record also records the target as it was at creation (`SceneIdentity`): identity material (device ID for block devices, file ID for images), evidence kind, carrier capacity, loop mapping (offset and sizelimit) and carrier file identity; before replay or resume every field is compared, and any **comparable field** that differs is a refusal. Evidence kind is an identity field: a record written for one kind does not match a target that reports another. File ID is `(st_dev, st_ino)` on Unix and volume serial plus file index on Windows; the volume serial is a profile field and does not participate in the identity decision. Capacity and carrier file ID are compared only when both sides provide them; a missing item does not participate, and the loop mapping must match — a mapping on one side and none on the other counts as a mismatch. Capacity alone does not identify a target: a replacement file of the same size can still pass. A target with no stable identity at all (`Unusable`) is refused **before any byte is written**: such a scene could neither be resumed nor undone, so the dead end must not be discovered at recovery time; a record left with "no evidence" never matches any current target, and the pre-replay check refuses it with 3 and a reason.

## Disk GUID credential in a record

Beyond the identity section, the record (format v6, magic `DSKR`) stores the target's GPT disk GUID in three states: `Present` / `Unavailable` / `GeneratedThisOperation`. `Present` must agree with the disk; `Unavailable` means there is no readable GPT on the target (MBR / unpartitioned) and constitutes no evidence; `GeneratedThisOperation` appears only on the record side (the whole table was generated by the operation that wrote the record) and is not compared with the disk GUID. Both sides `Present` with different values, record `Present` while the target has no readable GPT, and record `Unavailable` while the target now carries a GPT are all identity mismatches. **Old formats are not migrated**: a record format version this build does not recognise is `UnrecognizedFormat`, write commands refuse with 3, and this build neither replays nor migrates it. `abandon`'s automatic quarantine requires the header, version, identity-section CRC and identity chain to all pass. `undo` refuses an old undo journal with 3, stating that it predates the record format; it is not migrated, replayed or deleted, and when its existence cannot be determined the command refuses with 4.

## Placement of the recovery record

A recovery record is a regular file at its location (`<image>.diskedit/record` for images, `<state_root>/recovery/<identity-hash>/record` for block devices). What sits at that location is answered by one probe: absent, decodable, damaged (torn or CRC mismatch), an unrecognised format version, not a recovery file (symbolic link / directory / non-regular file), or unreadable. On Linux the path is resolved from the parent-directory anchor with successive `openat(O_NOFOLLOW|O_DIRECTORY)`, and the final component with `O_NOFOLLOW`: a symbolic link at any level, a non-directory, or a non-regular file at the last component all count as "not a recovery file". Non-Linux is a reserved port: it answers existence with `symlink_metadata` only and never reads the content, so a regular file there is refused as "unreadable" — on that platform this build can refuse but cannot read a record. Removal and renaming act on that path entry itself (parent directory fd plus relative name), following no link and changing no link target; atomic replacement is a rename within the same directory. When the entry is not a recovery file, or removal fails, the scene is treated as still present and the tool does not report it clean.

## Directory-entry persistence on Windows

After removing or renaming a recovery file, the tool does not claim the directory entry reached the disk; it prints only `note: removed <path>; persistence of the directory entry was not verified on this platform` (likewise for renaming). The platform offers no power-loss durability guarantee for directory entries, so this note must not be read as "already persisted".

## Resume boundary

Re-running the original command resumes from its recovery record for `new`, `move`, `resize-part`, `mkfs`, `resizefs`, `set` and GPT `resize`; `add`, `delete` and `copy` have no resume path (`help copy` states `No resume`), so roll back with `undo` or release the scene with `abandon` before re-running. An interrupted MBR `resize` prints `note: MBR has no recovery record — if this grow is interrupted, inspect the partition table and filesystem size before re-running`; re-running is not resuming. The shrink step records three states (not shrunk / verified / unverified): when the filesystem size cannot be read back, the job stops at the shrink step and reports an unfinished transaction with exit code 5, and a re-run first reads the actual size and only repeats the shrink after confirming it never happened. At finish time the recovery record is deleted only when six conditions all hold: the record is recognisable, its commit state is committed, the identity matches, persistence is confirmed, the postcondition read-back passes, and the table-write step has completed. Otherwise the record is kept and the tool prints `the recovery record was not cleaned up (<reason>) — release it with diskedit abandon`. When the deletion itself fails, the transaction reports exit code 5 rather than success. Relocated data is synced in batches that advance the durable cursor (the sync precedes the record advance, and the cursor never runs ahead of bytes actually on disk); the batch size adapts to commit latency, so after a crash at most 256 MiB of copied data is redone, and block sizes larger than that window degrade to per-block commits. A self-overlapping relocation (displacement smaller than the source range) commits block by block on every path — blocks buffered by batching would reach into the redo range, and the redo would read source data overwritten by that same batch.

## OpenWrt combined layout

A read-only squashfs/erofs root plus a trailing RW overlay in the same partition: a grow identifies the inner filesystem and extends only the RW layer through an offset loop, and only ever grows; an inner filesystem other than ext or f2fs is refused. A trailing RW layer that is not yet formatted (first-boot install scene) is not a failure: the partition still grows, and the layer is initialised by fstools on first mount, leaving nothing to do here. Multi-device btrfs is refused for grow.

## Verification scope

The tool works against the command-line contracts of Linux `util-linux` and the official per-filesystem tools and is not tied to a distribution; the regression suite (`tests/wsl/`) is verified on Ubuntu with `util-linux` 2.41.3, and other distributions and versions are unverified. Occupancy probing is recorded in the grades below; paths that have not been run are not described as passing:

| Evidence grade | Content |
|---|---|
| run and verified | loop identity encoding (`st_dev`/`st_ino` against `lo_device`/`lo_inode`), `ENXIO` for an unbound loop, hard-link aliases and deleted backing paths, mounts in other mount namespaces, loop and partition mounts, active swap, sysfs holders, mountinfo of an exited process (`EINVAL`), fail-closed probing (exit code 4), the full `--grow-lv` chain on an LVM PV with no holder, `AllowDm` not rejected by the general rule when an active LV holds the partition (the chain reaches the LVM step) while a whole-range `mkfs` rewrite is still refused, all of `new`/`add`/`delete`/`set name\|type\|flag`/`undo` refused on a mounted image with the disk bytes unchanged, a refusal that names the actual holder when several loops match, image operations usable by a non-root user (who cannot open `root:disk` loop nodes) |
| unverified | completeness of loop enumeration under containers with an independent PID namespace; deployments where mountinfo is unreadable because of permission limits such as `hidepid` (the code refuses as a failed probe, but it has not been run in a real `hidepid` environment); distributions and kernel versions outside the table above; **the full `--grow-lv` finish chain when the PV inside the image is mapped by another loop and the VG has an active LV** (see the section above: LVM's duplicate-PV rule makes `pvresize` on the temporary mapping a no-op, and the tool reports exit code 5 without claiming success) |
| design limit | the occupancy gate is a point-in-time decision before writing and does not stop an external loop / swap / mount created after the check; image-side enumeration covers only loop nodes visible to this process, and a node that cannot be opened for lack of permission (`root:disk`) is skipped as unbound — creating a binding and accessing the node require the same permission class, so such a user cannot create a binding to this image; a node that does not exist, `ENODEV`, and other cases where identity cannot be confirmed are refused as a failed probe, and this boundary moves with the kernel/udev permission model; fail-closed applies to a failed probe of an unrelated loop as well; a missing record item (`None`) does not participate in the comparison |
